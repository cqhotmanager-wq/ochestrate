# 企业级智能体平台开发手册

本文档面向开发者，重点说明系统功能作用、核心调用链路以及如何进行二次开发。  
定位上与 `docs/中文使用说明.md` 互补：使用说明偏“怎么用”，本手册偏“怎么改、怎么验”。

## 1. 系统能力地图

平台目标是同时支撑两条主线：

- 知识问答：RAG + 多智能体协同输出答案与引用。
- 自动化执行：任务入队、异步执行、状态追踪、审计留痕。

核心能力拆分如下：

- 接入与协议：`app/api/v1`  
  作用：统一暴露鉴权、智能体、任务、知识、技能、反馈等接口。
- 认证与租户隔离：`app/auth` + `app/middleware`  
  作用：基于 JWT 强制请求绑定 `tenant_id/user_id/role`，避免请求体伪造身份。
- 编排执行：`app/orchestration` + `app/agents`  
  作用：按 Planner -> Retriever -> Executor -> Reviewer 流程组织执行。
- 模型路由：`app/models`  
  作用：依据任务类型和敏感等级路由模型，失败时按策略回退。
- 工具调用：`app/tools`  
  作用：统一工具注册、权限校验、幂等处理与审计记录。
- 记忆与上下文：`app/memory` + `app/context` + `app/prompts`  
  作用：拼装系统提示、短期/长期记忆、证据与技能上下文。
- 数据与可靠性：`app/storage` + `app/workers`  
  作用：任务状态持久化、反馈与审计落库、队列消费与恢复。
- 可观测性：`app/observability`  
  作用：指标、trace、审计事件，支撑线上排障与质量优化。

## 2. 核心请求生命周期

### 2.1 同步请求（`POST /v1/agent/run`）

1. 请求进入 FastAPI 路由，`AuthContextMiddleware` 解析 Bearer Token。  
为什么：统一身份入口，避免各路由重复鉴权代码。
2. `bind_unified_request_auth` 覆盖请求中的租户/用户字段。  
为什么：不信任请求体同名字段，确保租户隔离。
3. `OrchestratorService.run` 创建 trace，执行编排图或串行回退链路。  
为什么：LangGraph 可用时保证结构化流程，不可用时保证服务降级可用。
4. 编排流程中完成规划、检索、工具动作、模型生成与评审。  
为什么：拆分职责有利于后续替换单节点策略。
5. 写入记忆、指标、审计并返回 `UnifiedResponse`。  
为什么：为后续会话增强和线上诊断保留上下文。

### 2.2 异步请求（`POST /v1/tasks/submit` + SSE）

1. 路由提交任务，`TaskManager.submit` 同时写入内存态和持久态。  
为什么：保证进程重启后仍可恢复任务。
2. 任务 ID 入队，由 `TaskManager._worker_loop` 消费执行。  
为什么：隔离长耗时执行，避免阻塞 API 请求线程。
3. 执行状态更新 `queued/running/completed/failed` 并广播给订阅端。  
为什么：SSE 端可实时展示进度与最终结果。
4. 启动阶段 `_recover_pending_tasks` 重新拉起 `queued/running` 任务。  
为什么：提升任务可靠性，降低异常中断损失。

## 3. 关键模块协作与开发入口

### 3.1 API 层（`app/api/v1`）

- 改动入口：新增/调整请求参数与路由校验逻辑。
- 注意事项：
  - 路由层必须依赖 `require_auth_context`（匿名接口除外）。
  - 请求中的身份字段必须通过 `bind_*_auth` 统一覆盖。
- 验证方式：
  - 单测：参数校验、权限拦截、状态码语义。
  - 集成：登录后调用目标接口，验证租户隔离。

### 3.2 编排层（`app/orchestration`、`app/agents`）

- 改动入口：新增节点、调整节点顺序、增强节点输入输出。
- 注意事项：
  - `UnifiedRequest/UnifiedResponse` 结构保持向后兼容。
  - 变更节点时同步检查 `_run_without_graph` 回退路径。
- 验证方式：
  - 低成本任务（如简单问答）验证端到端可用。
  - 故意关闭/移除 LangGraph 依赖验证回退链路。

### 3.3 工具层（`app/tools`）

- 改动入口：新增工具类并注册到 `ToolHub`。
- 注意事项：
  - 明确 `required_roles`、`idempotent`、输入参数校验。
  - 涉及 I/O 必须走 `ToolSecurityConfig` 的路径/域名/协议限制。
- 验证方式：
  - 单测覆盖允许与拒绝路径、异常路径、幂等命中路径。

### 3.4 存储与任务层（`app/storage`、`app/workers`）

- 改动入口：任务状态字段、仓储查询、恢复策略。
- 注意事项：
  - 所有任务状态流转必须同步内存态与持久态。
  - 仓储层应同时兼容 DB 模式和内存模式（dev/test）。
- 验证方式：
  - 重启恢复验证：提交任务后中断服务并重启，确认任务继续执行。

## 4. 开发环境与启动流程

### 4.1 本地启动

```powershell
uv sync --extra dev
docker compose up -d mysql etcd minio milvus

$env:AGENT_ENV = "dev"
$env:AGENT_MYSQL_DSN = "mysql+pymysql://root:123456@127.0.0.1:3306/ochestrate"
$env:AGENT_MODEL_ROUTING_PATH = "config/model_routing.yaml"
$env:AGENT_TOOL_SECURITY_PATH = "config/tool_security.yaml"
$env:AGENT_JWT_SECRET = "change-this-secret"
$env:AGENT_TASK_QUEUE_BACKEND = "memory"

uv run alembic upgrade head
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

### 4.2 最小验证链路

1. `POST /v1/auth/bootstrap-admin`
2. `POST /v1/auth/login`
3. `POST /v1/knowledge/ingest-text`
4. `POST /v1/agent/run`
5. `POST /v1/tasks/submit` + `GET /v1/tasks/{task_id}/events`

## 5. 常见二开场景（为什么 + 怎么改 + 如何验证）

### 5.1 新增 API 接口

- 为什么：新增业务能力的统一入口。
- 怎么改：
  - 在 `app/schemas/api.py` 增加请求/响应模型。
  - 在 `app/api/v1` 新增路由并接入鉴权依赖。
  - 在 `app/api/v1/router.py` 注册新路由。
- 如何验证：
  - 单测覆盖参数校验与权限。
  - 集成测试覆盖成功路径与拒绝路径。

### 5.2 新增工具能力

- 为什么：扩展可执行动作（文件、数据库、外部服务）。
- 怎么改：
  - 在 `app/tools` 增加工具实现，声明角色与幂等属性。
  - 在 `app/core/dependencies.py` 的工具注册流程接入。
  - 必要时扩展 `config/tool_security.yaml`。
- 如何验证：
  - 单测覆盖安全策略（路径/域名/写保护/租户过滤）。
  - 在 `POST /v1/agent/run` 中验证工具被正确调用并有审计记录。

### 5.3 扩展模型路由策略

- 为什么：按任务类型和数据敏感度控制成本与质量。
- 怎么改：
  - 修改 `config/model_routing.yaml` 的 `rules/providers/fallback_order`。
  - 如需新 provider，在 `app/models/providers.py` 增加客户端实现并注册。
- 如何验证：
  - 构造不同 `task_type + sensitivity` 请求，确认命中预期 provider。
  - 模拟主 provider 异常，验证回退顺序生效。

### 5.4 调整任务执行流程

- 为什么：引入新阶段或优化执行顺序/容错。
- 怎么改：
  - 修改 `OrchestratorService` 的状态图和回退串行流程。
  - 校准任务状态更新与 SSE 推送语义。
- 如何验证：
  - 同步接口验证结果正确。
  - 异步任务验证状态流转完整：`queued -> running -> completed/failed`。

### 5.5 新增存储字段与迁移

- 为什么：持久化新业务数据。
- 怎么改：
  - 更新 ORM 模型（`app/storage/models.py`）。
  - 新增 Alembic 迁移并升级。
  - 仓储读写逻辑同步适配。
- 如何验证：
  - 本地执行 `uv run alembic upgrade head`。
  - 读写接口回归测试，确认字段落库与读取一致。

## 6. 测试策略

- 基线命令：`python -m pytest -q`
- 建议分层：
  - 单测：工具安全、模型路由、仓储行为、提示词组装。
  - 集成：认证 -> 业务接口 -> 任务流转 -> SSE 事件。
- 关键断言：
  - 鉴权上下文覆盖请求体身份字段。
  - 租户隔离不可被跨租户读取绕过。
  - 工具审计与任务状态持久化一致。

## 7. 调试与排障

### 7.1 常见问题定位顺序

1. 看接口返回与状态码（是否是参数/权限问题）。
2. 看任务状态表与 SSE 事件（是否队列消费异常）。
3. 看审计事件与 metrics（是否工具调用或模型回退异常）。
4. 看配置文件与环境变量（是否路径、DSN、密钥、队列后端不一致）。

### 7.2 高频问题与处理建议

- 登录失败：优先检查 `AGENT_JWT_SECRET` 与数据库用户状态。
- 提交任务不执行：检查 `AGENT_TASK_QUEUE_BACKEND` 与 worker 是否启动。
- 工具访问被拒绝：检查 `tool_security.yaml` 的白名单与私网拦截策略。
- 结果质量不稳定：检查模型路由规则与 `fallback_order` 命中情况。

## 8. 发布前检查清单

- 已执行 `python -m pytest -q` 且全部通过。
- 关键接口手工冒烟通过：登录、`/v1/agent/run`、`/v1/tasks/submit`、SSE、知识摄取。
- 迁移脚本可重复执行并可回滚（如有 schema 变更）。
- 关键配置项已在目标环境注入（DSN、JWT、模型路由、工具安全）。
- 审计日志与 metrics 正常输出，便于上线后观测。
